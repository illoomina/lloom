The OpenAI-compatible endpoint and the pipette benchmark sidecar contract on a loopback port

Usage: lloom serve [OPTIONS]

Options:
      --model <MODEL>
          The model: an LFM2 checkpoint directory (config.json, tokenizer.json, *.safetensors, chat_template.jinja) or a Qwen4-exp GGUF (the first shard, `-00001-of-0000N`; its siblings are found beside it, or a directory holding them). Defaults to LFM2_MODEL_DIR, then the LFM2.5-2.6B snapshot in the HF cache
      --model-name <MODEL_NAME>
          The `model` id reported by `/v1/models` and accepted by requests. Defaults to the checkpoint's Hub id when it is a HF-cache snapshot
      --no-warmup
          Skip the pipeline warmup at load (the first prompt then compiles the prefill pipelines inside its own TTFT)
      --cpu
          Force the CPU device
      --tokenizer <TOKENIZER>
          Qwen4-exp: tokenizer.json (with chat_template.jinja beside it). Default: the HF cache's Qwen/Qwen3.8-Flash-Next snapshot
      --experts <EXPERTS>
          Qwen4-exp: how the routed experts are held — `stream` (a slot pool per layer filled from the checkpoint on demand, the tier that fits this machine; `expert-streaming.md` §20) or `resident` (every expert in memory) [default: stream]
      --loader <LOADER>
          Qwen4-exp, `--experts stream`: the loader primitive, `pread` (read + compute-encoder copy) or `io` (`MTLIOCommandQueue`) [default: pread]
      --ple-cache-rows <PLE_CACHE_ROWS>
          Qwen4-exp: rows of the N-gram PLE hot-row cache (0 = read the memory map every gather) [default: 0]
      --no-ple
          Qwen4-exp: load without the N-gram PLE (a measurement arm; the digests belong to the PLE-on model)
      --moe-act <MOE_ACT>
          Qwen4-exp: the routed experts' activation dtype — `auto` (`f16` under the `fast` contract, `f32` under `deterministic`), `f32` (the byte-identical routed arm) or `f16` [default: auto]
      --hotlist <HOTLIST>
          Qwen4-exp `--experts stream`: the expert hotlist file — read at load to warm every layer's pool before the first request (§20.3 R2; a missing file warms nothing), written at shutdown with the usage since load merged in
      --prefetch [<BOOL>]
          Qwen4-exp `--experts stream`: the expert prefetcher (the streamed tier's reads off the encoding thread, ahead of the layer; §20.4) [default: true] [possible values: true, false]
      --io-hints [<BOOL>]
          Qwen4-exp `--experts stream --loader io`: the in-flight residency hints into free slots (measured not to pay on a pool smaller than the tile; off) [default: false] [possible values: true, false]
      --prefill-mode <chunk|replay>
          Qwen4-exp: how a prompt is prefilled — `chunk` (the chunked DeltaNet / QSA passes) or `replay` (the decode recurrence replayed per token; a reference arm) [default: chunk]
      --pin <PIN>
          Qwen4-exp `--experts stream --hotlist`: pin this many experts per layer from the hotlist (never evicted); 0 = none [default: 0]
      --flash-k <K>
          LFM2, under `--attn flash`: pages per FlashDecoding chunk (`k` of `chunk_size = k × page_size`; 1, the shipped value, is a 256-key chunk per partial threadgroup). A probe of the partial kernel's geometry at long context; `k > 1` needs the pool's pages chunk-contiguous, which a fresh single-sequence pool is and a recycled one is not (§10.3d)
      --host <HOST>
          Bind address. Loopback: this is a sidecar, not a public server [default: 127.0.0.1]
      --port <PORT>
          Port; 0 picks a free one. The bound port is in the ready marker [default: 0]
      --config <PATH>
          A JSON file of option groups (`{"decode": {...}}`) — what `lloom config` prints, read back. Applied over the defaults and the env aliases
      --decode-config <JSON>
          The decode group as JSON (`'{"readback": "ring-hostdrain", "in_flight": 2}'`)
      --tuning-config <JSON>
          The tuning group as JSON (`'{"qmv": {"q6k_nr0": 4}, "metal": {"cut_policy": "node-aligned"}}'`)
      --model-config <JSON>
          The model group as JSON (`'{"cache": "crown", "axes": {"attn": "flash", "kv-append": "paged"}}'`)
      --speculative-config <JSON>
          The speculative group as JSON (`'{"method": "mtp", "k": 2, "drafter": "…gguf"}'`)
      --executor-config <JSON>
          The executor group as JSON (`'{"replay": true, "replay_barriers": "always"}'`)
      --memory-config <JSON>
          The memory group as JSON (`'{"memory_fraction": 0.75, "kv_capacity": 4096, "slots": "200"}'`)
      --generation-config <JSON>
          The sampling group as JSON (`'{"temperature": 0.7, "top_p": 0.9, "max_tokens": 256}'`; vLLM's name)
      --speculate <METHOD>
          The speculative body by name (`speculative.method`): `none`, `dspark`, `mtp`, `dflash` (Qwen4-exp's block drafter), or `auto` — the family's own drafter when one is at hand. `--dspark` and `--mtp` override it
      --dspark
          LFM2: the speculative body (`speculative.method = dspark`): a DSpark drafter proposes a block per round, the target verifies it in one pass. Loads the newest LFM2.5-2.6B-DSpark snapshot in the HF cache, or `--draft-dir`
      --draft-dir <DIR>
          The block drafter's checkpoint directory (`speculative.drafter`): LFM2's DSpark under `--dspark`, Qwen4-exp's DFlash under `--speculate dflash`
      --dspark-k <DSPARK_K>
          Under `--dspark` (LFM2) or `--speculate dflash` (Qwen4-exp): propose this many positions per round (default: LFM2 the block, 9; Qwen4-exp 3 of its 7), clamped to the block (`speculative.k`)
      --mtp <GGUF>
          Qwen4-exp: the GGUF carrying the MTP head (`blk.{n_layers}.*` + `nextn.*`, the sidecar `qwen4exp-mtp-quantize write` produces); `speculative.method = mtp`, `speculative.drafter`
      --mtp-k <MTP_K>
          Qwen4-exp `--mtp`: tokens the drafter proposes per round (`speculative.k`)
      --set <KEY=VALUE>
          One knob by dotted key, repeatable (`--set decode.readback.eos=gpu-batched`)
      --readback <SPELLING>
          The token mechanisms; `--readback <spelling>` is the shorthand. (a shorthand for the group's keys)
      --kind <READBACKKIND>
          The strategy: `auto` (the ring where the sampler admits it), `blocking`, `ring`. [arms: auto, blocking, ring]
      --eos <EOSKIND>
          How a ring learns EOS. [arms: blocking, poll, host-drain, gpu-batched, gpu-batched-nonblocking]
      --poll <POLLMECHANISM>
          The poll mechanism under `eos = poll` (`wfe` on aarch64 by default). [arms: spin, spin-hint, wfe, sleep, sleep:<µs>]
      --lookahead <USIZE>
          Forward passes the host enqueues before it has learned the previous step's EOS (ring arms): 0 or 1. [arms: 0, 1]
      --commit-budget <COMMITBUDGET>
          How often the loop commits and prunes the in-flight queue: `per-token` or `steps:<N>`. [arms: per-token, steps:<N>]
      --adaptive-commit [<BOOL>]
          The adaptive commit (lloom #735): a buffer closes when the GPU starts the previous one, no cadence; needs a ring arm and lookahead 1, drains through the reader [possible values: true, false]
      --run-ahead <USIZE>
          Under the adaptive commit: the most steps one buffer holds before it closes regardless (0 = 8)
      --eos-gate [<BOOL>]
          The EOS gate: the kernels queued past an EOS return at once, so the cache ends at the EOS. Rides the adaptive commit; off where the adaptive commit does not run, or under the ICB replay executor [possible values: true, false]
      --fused-publish [<BOOL>]
          Under the adaptive commit: publish with the fused argmax·eos·stamp kernel (off = the six-launch chain, the A/B arm) [possible values: true, false]
      --stream-reader [<BOOL>]
          Stream tokens off a ring-reader thread per token instead of the loop's commit-cadence drain (ring arms; implied by the adaptive commit) [possible values: true, false]
      --wake-cadence <USIZE>
          Commits between live completion-marker writes on the deferred-marker arms (`host-drain`, `gpu-batched*`)
      --in-flight <USIZE>
          How many forwards the host may run ahead of the GPU (the pacer's bound); 0 = the depth warmup measured. [env: LLOOM_IN_FLIGHT]
      --phase-sync [<BOOL>]
          Diagnostic, perturbs what it measures: drain the GPU per phase of a speculative round [possible values: true, false]
      --prefill-tile <USIZE>
          The TILE: the most prompt tokens one prefill forward takes (llama.cpp's `n_ubatch`); 0 = the whole prompt in one forward
      --prefill-ubatch <USIZE>
          The spark: how many prompt tokens the FIRST forward takes, the remainder in one more (0 = one-shot)
      --prefill-chunk <USIZE>
          The CHUNK under `--batch N`: the most prompt tokens fed per batched step as extra ragged rows (0 = a whole prompt at its arrival)
      --spark <STRING>
          An aligned-bucket schedule for the prefill forwards: `N` or `progressive:START,STOP`, optionally `/tile:BULK`. [arms: 1, 16, 32, 64, progressive:START,STOP, …/tile:BULK]
      --pass-widths <PASSWIDTHS>
          How a batched step's prompt pieces are sized: `lru` or `ladder` (DESIGN §9.2aa I4). [arms: lru, ladder]
      --prefill-in-flight <USIZE>
          The pacer's in-flight bound during prefill (0 = decode's depth). [env: LLOOM_PREFILL_IN_FLIGHT]
      --profile <STRING>
          The determinism contract: `fast` (the default: the same distribution; licenses the arms whose bits depend on scheduling or batch composition) or `deterministic` (same inputs + seed → same bits; every gate pins it). [arms: deterministic, fast] [env: LLOOM_PROFILE]
      --gemm-skinny-max <USIZE>
